# DevCleaner v1 — Consolidated Requirements & Architecture Review

**Статус:** consolidated requirements baseline / safety policies confirmed; issue drafts remain unpublished  
**Дата:** 2026-10-15  
**Источник:** 92 ответа в requirements discovery interview, подтверждённый выбор B по Q93, уточнение Q25 (без автоматического удаления карантина) и утверждённые сквозные архитектурные требования к F#/OpenCode.  
**Применение:** основной исходный материал для GitHub Project, milestones, GitHub Issues и независимого PR review.  

> Документ фиксирует **что система должна делать, границы полномочий и проверяемые ограничения**, а не предписывает внутреннюю реализацию агентам OpenCode. Термины v1 и MVP в этом документе означают целевой первый полный релиз; его функциональность может поставляться несколькими промежуточными работоспособными сборками.

## 1. Цель, платформа и границы v1

**Цель.** Портативное desktop-приложение для Windows 11, которое обнаруживает кандидатов на очистку, выясняет их происхождение, классифицирует риск и выполняет безопасные, контролируемые пользователем файловые операции. Неизвестные объекты исследуются с помощью LLM; системные компоненты Windows в v1 только инвентаризируются и анализируются.

**Зафиксированные решения:**

- Windows 11 x64; F# и .NET 11; desktop UI в эстетике Material Design 3, ориентир — Avalonia. Не требуется поддержка иных ОС и архитектур в v1.
- Одно окно, четыре вкладки: **Cleanup**, **Windows Investigation**, **Quarantine**, **History**. UI и вывод LLM на английском. Светлая/тёмная тема в первоначальной концепции; конкретные UI-компоненты — выбор агентов.
- Ручной запуск сканирования. Сохраняемые профили, в том числе готовые и пользовательские, с гибким выбором каталогов, категорий и Windows-подсистем. Фонового сканирования и расписаний нет.
- Обычная работа без elevation; UAC для отдельных операций, которым действительно требуются дополнительные права.
- Local-first / offline-first для сканирования и очистки; интернет требуется только для внешних LLM и веб-исследований.
- **Включено в v1:** файловая очистка, классификация и управление правилами, LLM investigation, широкий read-only обзор Windows, восстановление файлового карантина, журналирование операций.
- **Не входит в v1:** удаление/изменение служб, драйверов, scheduled tasks, ключей реестра, firewall rules, shell extensions и других компонентов Windows; автоматический автономный контроль системы; встроенный updater; Windows toast-уведомления; Git maintenance; управление Windows Recycle Bin.

## 1A. Общий инженерный контракт (обязателен для каждой GitHub Issue)

Это **сквозные архитектурные и инженерные требования**: они действуют во всех задачах, включая небольшие UI-изменения и инфраструктурные работы. Они не диктуют конкретные классы, имена файлов, библиотеки или механизмы исполнения. Агент самостоятельно выбирает наименьшее корректное решение и отражает значимые компромиссы в обязательном Preflight/PR review.

1. **Модульность по функциональным границам.** Независимые семейства детекторов, классификаторов, Windows-проверок и интеграций должны иметь локализованную реализацию и явный контракт взаимодействия с остальной системой. Добавление новой независимой проверки не должно требовать изменения несвязанных проверок или разрастания единого условного диспетчера. Не создавать отдельный модуль/проект/интерфейс ради каждого trivial helper и не строить speculative plugin frameworks: модульность пропорциональна реальной независимости ответственности.
2. **Функциональный подход по умолчанию.** Для преобразований, классификации, правил, решений о риске и валидации предпочитать чистые функции, неизменяемые данные и композицию. Использовать идиоматические возможности современного F# (records, discriminated unions, pattern matching, функции высшего порядка и типизацию состояний) там, где это повышает корректность и читаемость; побочные эффекты явно отделять на границах файловой системы, Windows API, сети, хранения и UI. Не заменять подходящие платформенные API собственной реализацией ради «функциональной чистоты».
3. **Ожидаемые ошибки — в типизированные результаты.** Предсказуемые ошибки операций (например, access denied, file missing, conflicts, malformed provider response) должны возвращаться через `Result<'T, 'Error>` либо эквивалентный явный доменный результат. Исключения, возникающие из внешних .NET/Windows API, переводить на границах интеграции в осмысленные доменные ошибки посредством локального `try/with` или эквивалентного корректного механизма. Вызывающий код должен явно обрабатывать успех/неуспех. Для асинхронных операций допускается `Task<Result<_,_>>`/`Async<Result<_,_>>`; не вводить собственный универсальный effect framework без потребности.
4. **Не скрывать нарушения инвариантов.** Не делать blanket `catch-all` повсеместно и не превращать программистские ошибки, повреждение инвариантов, критические runtime failures или отмену (`OperationCanceledException`) в фиктивный успех. Сохранять штатную семантику отмены, resource lifetime и корректное освобождение ресурсов; если продолжение небезопасно, fail closed с диагностикой. Не обещать, что в исполняющем процессе вообще не могут возникать исключения.
5. **Композиция, DRY и код, который легко читать.** Приоритет — маленькие связные единицы логики, говорящие имена, очевидные контракты и локальный поток данных. Переиспользовать только действительно общие правила/логику, избегая дублирования бизнес-инвариантов; допустима небольшая структурная повторяемость вместо преждевременной универсальной абстракции. Избегать "spaghetti code", скрытого состояния и сверхсложной иерархии абстракций.
6. **Канонические правила OpenCode.** Перед работой агент обязан загрузить актуальные существующие инструкции проекта OpenCode для F#, комментариев и обозначенного пользователем подхода **«one word»**, если он определён в этих инструкциях. Не выдумывать трактовку непроверенного внутреннего термина; при отсутствии определения — зафиксировать вопрос на Preflight. Комментарии должны следовать каноническим правилам и не заменять ясность кода.
7. **Проверяемость без overengineering.** Тестировать критические инварианты безопасности и границы сбоев, остальные сценарии — пропорционально риску (Q50). Не внедрять generic frameworks, compatibility layers, дополнительные проекты и расширение scope без доказуемой пользы и разрешения пользователя. Существенные отклонения от функционального/модульного подхода объяснять в PR.

**Приоритет требований:** безопасность/ограничения полномочий и согласованные acceptance criteria имеют приоритет над стилистическими предпочтениями. `Result` не должен скрывать ошибки или обходить fail-closed поведение.

## 2. Functional requirements

### 2.1 Discovery / scanning (Q2–Q10, Q43, Q46–Q48)

- Профили сканирования: предустановленные и пользовательские; можно выбирать директории и виды Windows-артефактов; глобальные исключения работают независимо от профиля.
- Сканирование включает локальные, внешние и явно выбранные сетевые расположения. Для network shares допускается только read-only. Файловые ссылки обнаруживаются, но обход их целей по умолчанию не выполняется.
- Адаптивный анализ: в первую очередь файловые метаданные и структура; при необходимости — углублённое локальное чтение допустимых файлов. Для архивов содержимое не исследуется, архив рассматривается единым объектом.
- Временные ошибки сканирования обрабатываются контролируемыми повторными попытками; возможно явное получение разрешения UAC или попытка восстановить доступное подключение. Нельзя автоматически изменять ACL или обходить ограничения ОС.
- Ошибки отдельного объекта не останавливают независимые области анализа; результаты должны быть помечены как частичные, если это так.
- Пользователь видит прогресс, может поставить scan на паузу, продолжить или отменить. Результаты появляются постепенно. Возобновление незавершённого scan после перезапуска приложения не требуется.
- Иерархические результаты: группы по категориям, владельцам, проектам и локациям; раскрытие до отдельных файлов. Допустим выбор отдельных объектов и допустимых групп.
- Масштабируемость: нет фиксированного предела по числу объектов; обработка не должна требовать удержания всех файлов в RAM; отзывчивость UI обязательна. Режимы нагрузки: экономный, сбалансированный (по умолчанию), максимальный. Цель оптимизации — фактическая Windows 11 рабочая станция владельца.
- Предварительный расчёт логического объёма, физически занятого пространства и ожидаемого освобождения. Учитывать hard links, sparse/compressed files, облачные placeholders; при невозможности точной оценки явно помечать approximate.

### 2.2 Classification / deterministic rules (Q11–Q15, Q67–Q70, Q86)

- Конфигурация детерминированных правил — source of truth для известных категорий; встроенные и пользовательские правила различимы. Пользователь управляет правилами из UI, без ручного редактирования файла и без перезапуска приложения.
- Правило описывает тип, назначение, предполагаемого владельца, риск и обоснование. Оно **не санкционирует удаление**.
- Область правила: глобальная, ограниченная каталогом или профилем. Пользовательские новые правила по умолчанию ограниченные; область можно расширить вручную.
- Новое правило должно предварительно показать совпадения в имеющихся результатах, риск, пересечения с другими правилами и защищёнными объектами; активируется только после подтверждения. Активированное правило немедленно влияет на текущую классификацию, но не запускает очистку.
- **Risk:** Low, Medium, High. **States:** Unknown, Conflict, Protected / Never Delete — не дополнительные уровни риска.
- При противоречащих правилах — `Conflict`, блокировка очистки до разрешения конфликта пользователем. LLM не устраняет конфликт автоматически.
- Если доказательств недостаточно — `Unknown`. После LLM-исследования пользователь подтверждает классификацию отдельного объекта; создавать правило для этого необязательно.
- Подтверждение: Low — стандартное; Medium — предупреждение; High — отдельное явное подтверждение; Unknown/Conflict — блокировка. Protected/Never Delete — запрет вне зависимости от риска и согласия на cleanup.
- `Protected` — встроенные критические объекты; `Never Delete` — пользовательские объекты, доступные исследованию, но не очистке; `Exclude from Scan` — не исследовать. Эти запреты имеют приоритет над правилами и LLM.
- Для недавно изменённых объектов показывать дополнительное предупреждение; порог давности настраивается. Файловые атрибуты Hidden/System/ReadOnly сами по себе не определяют риск, но не отменяют защиту ОС.
- Для файлов, принадлежащих достоверно установленному активному приложению, блокировать очистку до закрытия программы и повторной проверки.

### 2.3 LLM Investigation (Q16–Q22, Q35–Q36, Q39–Q40, Q44, Q61–Q66)

- Поддержка нескольких настроенных LLM-провайдеров (например DeepSeek, OpenAI, OpenRouter и совместимые API), с выбором активной модели. Не вводить зависимость бизнес-правил от конкретного провайдера.
- Допускаются только модели, прошедшие проверку фактической поддержки необходимых контрактов (tool calling, structured output). Не требуется эмуляция функций несовместимых моделей.
- Запуск LLM Investigation вручную для одного, нескольких или всех Unknown; без автоматической отправки неизвестных объектов после scan. Предварительный просмотр оценки стоимости и одобрение пользователя обязательны.
- Многошаговое управляемое расследование: модель выбирает следующие read-only инструменты для поиска свидетельств (файловые метаданные, установленное ПО, службы, реестр и др.) при ограничениях числа шагов, времени и денег. Никакого произвольного shell, записи в реестр, остановки процессов или самостоятельной очистки.
- Расширенное веб-исследование по публичным источникам: поиск, переход по страницам, уточнение гипотез и сопоставление с локальными свидетельствами. Первичные источники имеют приоритет; выводы со ссылками; противоречия показывать, недостаточность данных => Unknown.
- Внешние веб-инструменты не имеют доступа к loopback, внутренним/частным сетям, локальным файлам или cookies авторизованной сессии; ограничения применяются также к redirects/разрешённым адресам. Веб-контент — недоверенный ввод и не источник команд.
- Публичный поиск разрешается пользователем перед исследованием; формируемые запросы минимизируют чувствительные данные. Если запрос нельзя безопасно составить — пропуск. Запросы и источники журналируются.
- Внешней модели по умолчанию передаются только необходимые метаданные. Передача фрагментов содержимого файла требует отдельного разрешения после просмотра и проверки на секреты (не гарантирует отсутствие всех секретов).
- Заключение включает предполагаемое назначение, несколько потенциальных владельцев при неоднозначности, риск, основания и ограничения. «Неизвестно» — допустимый результат. Самооценка confidence моделью не является объективной вероятностью.
- Предусмотрен постоянный кэш завершённых расследований с инвалидацией при существенных изменениях объекта и принудительным повторным исследованием. Результат кэша не превращается автоматически в правило.
- Журнал расследования в UI: фактически выполненные tool calls, свидетельства, ошибки, ссылки и token/cost usage; внутренние рассуждения модели не требуются.
- Progress и cancel для отдельных/пакетных исследований; сохранение завершённых результатов. Пауза и persistent queue не требуются. Удалённый API может тарифицировать запрос, даже если пользователь отменил локальное ожидание.
- Общий бюджет по умолчанию с переопределением для одного исследования; ограничения шагов и времени; стоимость может быть приблизительной. При ошибке — ограниченные retries, без автоматического fallback на другой провайдер. Другую модель пользователь выбирает вручную и отдельно подтверждает передачу данных.
- API-ключи не сохраняются DevCleaner: ввод в текущем сеансе или env variables. Они не должны попадать в логи, кэш, историю или конфигурацию. По умолчанию в истории не сохраняются полные запросы и чувствительные фрагменты файлов.

### 2.4 Cleanup / safety / recovery (Q9, Q15, Q23–Q28, Q67–Q84, Q86, Q91–Q92)

- Любая очистка предваряется **Dry Run**: список действий и исключений, причины, размеры и ожидаемая фактическая экономия по томам, список рисков, состояние System Restore, возможность скорректировать набор. Dry Run не меняет файлы и не создаёт Restore Point.
- Перед изменением каждого выбранного объекта перепроверить фактический путь, идентичность, тип, допустимость и состояние; изменившиеся/неопределённые объекты пропускать. Не допускать удаления нового объекта, появившегося по прежнему пути; TOCTOU-риски учитываются и во время исполнения.
- Частичная очистка дерева разрешена: только классифицированные, допустимые и подтверждённые потомки; Protected/Never Delete/Unknown/Conflict остаются. Родитель не удаляется, если сохранились файлы.
- Карантин **включён по умолчанию** и расположен **на исходном томе**. Перемещение внутри того же тома обычно само по себе не освобождает место. DevCleaner различает отправленный в карантин объём и реально освобождённое пространство.
- Если карантин технически недоступен, объект пропускается; прямое необратимое удаление допускается только после отдельного явного подтверждения. Никакого молчаливого fallback.
- Restore Point **включён по умолчанию**; попытка создания на каждую операцию после user approval, до изменения файлов. Если не создан — показать результат и запросить явное решение продолжать без новой точки. System Restore — защита системного состояния, **не резервная копия пользовательских файлов**.
- Карантин хранит исходные пути и достаточно метаданных для восстановления; значимые ACL/attributes/timestamps/ADS должны сохраняться по возможностям FS. Если заранее известно, что необходимые свойства будут потеряны, операцию блокировать. Контроль криптографического содержимого при восстановлении не требуется (выбор Q75).
- Восстановление строго в исходное место на том же **идентифицированном** томе, независимо от изменившейся буквы диска; при занятом пути, неопределённом томе или отсутствии карантинного объекта восстановление блокируется. Нет overwrite, merge и restore-to-alternate-location.
- Незавершённая очистка после crash/reboot должна обнаруживаться. Пользователь выбирает: resume (с revalidation), finish partial или rollback того, что ещё доступно в карантине. Необратимо удалённое rollback не восстанавливает. Ошибки и partial result фиксируются.
- **Автоматическая очистка карантина полностью запрещена.** Объекты хранятся до ручного восстановления или вручную инициированного и явно подтверждённого окончательного удаления. В UI допустим настраиваемый порог возраста (например, 7/14/30 дней) только для визуального выделения старых объектов; достижение порога никогда не запускает очистку, в том числе при старте приложения. Не нужны служба, расписание или фоновый purge.
- Сброс локального состояния **запрещён**, пока карантин не пуст или его содержимое невозможно достоверно определить. Предыдущее состояние/прошлая версия приложения могут понадобиться для восстановления. Автопоиск карантинов после сброса не требуется.
- Директория приложения, его состояние и все управляемые карантины полностью исключены из обычного scan/cleanup. Собственные логи и кэш очищаются отдельно из настроек.
- Сетевые shares: только read-only. Локальные и внешние тома: очистка только при наличии требуемых возможностей конкретной FS (NTFS, ReFS, exFAT, FAT32 и др.). Для symlink/junction не следовать цели; hard links учитывать и при невозможности безопасного воздействия блокировать операцию.
- Облачные синхронизируемые каталоги могут очищаться обычным способом с дополнительным предупреждением о синхронизации последствий. Для hydration files-on-demand — отдельное разрешение с оценкой объёма. Помещение в карантин не обещает откат синхронизированного изменения в облаке.
- Recycle Bin: в v1 только отображение размеров, без DevCleaner-очистки; стандартная очистка не должна затрагивать `$Recycle.Bin`.
- Заблокированные файлы пропускать, по возможности показывать блокирующий процесс/PID, предлагать закрыть приложение вручную, затем повторить операцию. Не завершать процессы автоматически.
- Для кэшей NuGet/npm/pnpm/Yarn и аналогичных управляемых хранилищ предпочтительны поддерживаемые штатные механизмы очистки. Нельзя обходить механизмы безопасности из-за наличия команды; если команда затрагивает внешние области, показать их и получить отдельное согласие на расширение scope; при неопределённых последствиях заблокировать. Нет произвольных shell-команд от LLM. **После выполнения проверить фактические изменения доступными средствами** (Q93 B), сопоставить ожидаемые и наблюдаемые результаты и реальную экономию места, если её можно определить; различать `Completed`, `Partially Completed`, `Failed`, `Unknown Result`. Не повторять автоматически потенциально разрушительную команду при неопределённом исходе. Историю и ошибки сохранять.

### 2.5 Windows Investigation — read-only (Q1, Q29–Q31)

- Максимальный целевой охват v1: Services, Startup, Installed Programs, Registry, Task Scheduler, Event Logs, Environment Variables, Drivers, Shell Extensions, Firewall Rules, Windows Update, WSL2, Docker, virtual disks.
- Поиск подозрительных/осиротевших компонентов производится по совокупности признаков: наличие бинарников, установленные приложения, издатель/подпись, связи и зависимости, признаки использования. «Не найден владелец» не равно «можно удалить».
- Связанные артефакты группируются по предполагаемым приложениям-владельцам с сохранением индивидуального риска и уровня доказательности.
- LLM может исследовать объекты и их группы. Изменения системных объектов и эксплуатационные команды (stop, disable, delete, registry modification, event-log clearing и т. п.) в v1 **запрещены**.
- Сведения Windows могут быть неполны без elevation; интерфейс должен различать недоступные и отсутствующие объекты.

### 2.6 Git-aware protection (Q87–Q90)

- Распознавать Git repositories, nested repos, submodules и worktrees; корректно определять принадлежность файлов рабочему дереву.
- Tracked files защищены, в том числе с незакоммиченными изменениями. Untracked/ignored не считаются автоматически безопасными — применяются обычные правила и investigation.
- `.git`, linked common metadata, внутренние object stores и Git LFS storage не включаются в обычное исследование/очистку. Допустимо читать необходимые Git-метаданные **только ради проверок защиты**.
- При ошибке Git-проверки очистка внутри затронутого репозитория блокируется; независимые расположения обрабатываются дальше. Перед фактическим удалением Git-состояние затронутых объектов проверяется повторно.
- Нет Git maintenance, pruning, reflog cleanup и команд изменения внутреннего Git-хранилища.

### 2.7 Desktop UX (Q32–Q37, Q60)
- Минималистичное однооконное приложение в стиле Material 3, четыре вкладки Cleanup / Windows Investigation / Quarantine / History.
- Результаты иерархические; панель сведений об объекте справа без перехода в отдельное окно.
- Комбинируемые фильтры: имя/путь, владелец, категория, риск, Unknown/Conflict/Protected, размер, возраст, происхождение классификации, сортировка. Сохраняемые наборы фильтров; фильтрация не меняет выбранное для cleanup.
- LLM-отчёт с expandable tool/evidence log, прогрессом и отменой; без внутреннего chain-of-thought.
- Прогресс и результаты — внутри приложения, без Windows notifications и без обязательного экспорта отчётов.
- Весь UI и LLM conclusions — английские; исходные имена и пути не переводятся.

## 3. Architecture, storage and operational constraints (Q38–Q49)

- Portable folder-based Windows x64 application без инсталлятора. Конфигурация, правила, профили, история и LLM-кэш находятся рядом с приложением, а карантин — на исходных томах. Каталог приложения должен быть доступен для записи.
- Single-instance **для общего хранилища состояния**; повторный запуск активирует уже открытое окно.
- В случае критической недоступности/повреждения локального состояния приложение прекращает работу; разрушительные операции блокируются. Отдельные автоматические режимы восстановления повреждённого store не обязательны.
- Roll-forward: старые форматы не обязаны поддерживаться. При несовместимости возможен явный сброс, **но только после полного восстановления/опустошения карантина**; нельзя незаметно уничтожить recovery state.
- Пользовательские данные минимизируются: заключения, метаданные, журнал инструментов и стоимость; не сохраняются чувствительные фрагменты файлов и полные LLM-запросы по умолчанию. Возможна очистка history/cache.
- Ресурсы: bounded-memory принцип при произвольном числе файлов, потоковые/постепенные результаты, отзывчивость UI; 3 режима нагрузки; нет жёсткого требования на поддержку слабых ПК.
- Локальная диагностика: нормальный и подробный режимы, управление объёмом/retention, просмотр логов из UI, без внешней телеметрии, без секретов.
- Реализация внутренних контрактов, формата хранилища, UI-компонентов, планировщика сканирования и системных адаптеров остаётся ответственностью OpenCode; их не следует диктовать в Issues без обоснованного invariant.

## 4. Safety invariants — общие для всех feature issues

1. Никакое правило, LLM-заключение или выбор в UI не отменяет Protected, Never Delete, Exclude from Scan и неизменяемые запреты системы.
2. Unknown и Conflict никогда не допускаются к удалению, пока состояние не разрешено разрешённым способом.
3. LLM и веб-контент не выполняют write/delete/stop/execute; только детерминированные контролируемые инструменты могут изменять файлы после user approval.
4. Очистка затрагивает исключительно явно разрешённые, проверенные перед исполнением объекты в допустимой области; объект, подменённый между scan и execution, не удаляется.
5. Операция очистки должна оставлять достаточную долговременную запись для последующего понимания частично выполненных действий; отсутствие записи => запрет начала новых разрушительных действий.
6. Карантин DevCleaner и его собственные файлы не являются кандидатами обычной очистки.
7. Любая очистка инициируется пользователем и подтверждается по применимой политике риска; **автоматическое или фоновое удаление запрещено, включая любые данные карантина**. Нет silent irreversible delete, silent expansion of cleanup scope, silent LLM-provider fallback, silent hydration of cloud data.
8. System Restore никогда не позиционируется как гарантированное восстановление удалённых пользовательских файлов.
9. Системная инвентаризация Windows остаётся read-only для v1.
10. Публичные веб-данные — недоверенный ввод; сетевые ограничения веб-инструментов действуют независимо от prompt модели.

## 5. Development & governance (Q50–Q59)

- GitHub Project как единая доска; Backlog, Ready, In Progress, In Review, Blocked, Done. Пользователь выбирает и запускает задачи; агенты обновляют статусы.
- GitHub Issue определяет Goal, Scope, Out of Scope, Acceptance Criteria, Dependencies, Constraints & Invariants, Verification; **не предписывает детали реализации**.
- Декомпозиция гибридная: главным образом вертикальные функциональные slices; независимые предпосылки выделяются отдельно; явный dependency graph. Независимые issues можно выполнять параллельно; промежуточные состояния — работоспособные.
- Каждый агент стартует через OpenCode/workflow-mcp `task` с идентификатором `GHI-<issue number>`.
- Для каждой issue обязателен Preflight относительно текущего main, проверка зависимостей, актуальности и противоречий; **план согласуется пользователем до изменения кода**.
- Любое расширение scope, включая полезный побочный рефакторинг, требует предварительного одобрения. Реализация внутри утверждённого scope — выбор агента.
- Отдельная короткая branch на issue, PR в `main`, trunk-based. После исправления замечаний независимого ревью и локальных проверок **агент делает merge сам**. При изменении кода после одобрения — повторная проверка.
- Каждый PR: issue reference, критерии и их статус, локальный build/test, архитектурные решения, уместные альтернативы и trade-offs, изменения контрактов, риски, ограничения. Глубина описания пропорциональна изменению.
- Risk-based testing: автоматические регрессии для safeguards удаления/карантина/restore/crash/правил/LLM-tool boundaries; остальное — минимальные проверки. Нет искусственного покрытия или backwards-compat tests.
- Нет GitHub Actions CI/CD в v1. Локальная сборка Windows x64 ZIP, ручные Git tags и ручная публикация в GitHub Releases. Нет updater.

### Нормативная заметка по System Restore и NuGet

- Microsoft документирует пропуск создания новой restore point при наличии недавней (в обычной конфигурации — в пределах 24 часов) с **успешным** API result: https://learn.microsoft.com/en-us/windows/win32/sr/calling-srsetrestorepoint
- System Restore не восстанавливает обычные пользовательские файлы: https://learn.microsoft.com/en-us/windows/win32/sr/about-system-restore
- Штатная очистка NuGet local resources может удалять общие кэши, включая global-packages, после чего проекты должны восстановить пакеты заново: https://learn.microsoft.com/en-us/nuget/consume-packages/managing-the-global-packages-and-cache-folders
- У файла может быть несколько hard links, и удаление одного имени не обязательно освобождает storage: https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/fsutil-hardlink
- На 2026-10-15 .NET 11.0.0-rc.2 (go-live), а официальный релиз намечен на ноябрь 2026: https://dotnet.microsoft.com/en-us/download/dotnet и https://dotnet.microsoft.com/en-us/conf

## 8. Confirmed follow-up decisions / known intentional trade-offs

- **Q25 уточнён (позднейшее решение пользователя):** автоматической очистки карантина нет ни при запуске, ни по сроку, ни в фоне. Настраиваемый порог возраста может только выделять объекты для ручного просмотра. Все необратимые удаления инициируются и подтверждаются пользователем.
- **Q93 = B (подтверждено):** после штатной очистки проверять доступные фактические изменения и различать Completed / Partially Completed / Failed / Unknown Result, логировать результаты; не повторять разрушительную команду вслепую.
- **Намеренно принято:** состояние карантина не самоописывающееся и восстановление зависит от состояния приложения (Q73 A); автоматическая реконструкция после повреждения store не обязательна (Q45 A). Это осознанный риск доступности восстановления.
- **Намеренно принято:** baseline v1 исследует почти всю Windows, но не изменяет системные объекты; implementation order определяется GitHub dependency graph.
- **Намеренно принято:** отсутствие CI/CD и обязательные локальные тесты/расширенный PR-отчёт. Risk-based quality gates сохраняются.
